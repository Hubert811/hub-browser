# 关键词搜索范式(Keyword Select)

> 来源:QuickBI order-detail 攻坚(2026-08-27,用户定调)。适用于**enum 多选大列表字段**
> (字段值成百上千条,弹层带搜索框与「添加左侧全部字段值」按钮的形态)。
> 这是该类字段的**默认范式**——逐值精确 pick 路线已废弃。

## 语义定调

**「搜索词 = 过滤器,结果集 = 选择集」**:

- 用户传入的关键词就是过滤意图,适配器搜关键词 → 把**全部匹配项**一次加选
- 想精确匹配某个值,把关键词写全即可——精确度控制权交给用户
- 搜索结果可能截断/分页,「添加左侧全部字段值」一次性全加,不漏不挑

### 为什么逐值精确 pick 必须废弃

order-detail 实证(2026-08-27):用户传「成都万科物业服务有限公司」,组件搜索是
**子串匹配**,唯一真实选项是「成都万科物业服务有限公司娇子台物业管理分公司」——
精确等值 pick 找不到目标,要么 no-option 失败,要么(旧实现缺陷)误勾错误项。
值为长名/互为前缀的场景,精确匹配天然失配;而全选匹配集才是搜索意图的完整表达。

## 实现链（QuickBI 共用内核 advanceSelectKeywordLoop，实测 6s 全绿）

级联字段与 enum 大列表字段是**同一 advance-select 弹层组件**（搜索框 .ant-input +
结果列表 .advance-select-items + 已添加(N) 计数 + 添加左侧全部字段值按钮）——
共用同一内核函数 `advanceSelectKeywordLoop(page, keywords, opts)`，调用方只负责
开弹层/幂等预检/确认/字段级断言（触发器与语义因字段类型而异）。此前该循环在
级联精确/级联普通/enum 关键词三处各写一份，用户指出后合并（2026-08-27）。

```
1. 开弹层:箭头 icon 触发(.advance-select-right-icon;有值态点 tag 不开)
   + 字段定位精确 label 优先、子串兜底(包含关系 label 陷阱)
2. 就绪锚点:懒加载大列表(「默认展示前1000条」)初始列表不可信
   → 就绪条件降为「搜索框可用」，反正要走搜索
3. 残留清空:「已添加(N)」N>0 先点「清空」——残留 ∪ 搜索结果语义错
4. settle 800ms:弹层刚开时输入处理器未挂好——立即打字 onChange 不触发
   （实证:值进了但自动搜索不发起，db-search 点击也不发请求）
5. 输入关键词:eval 内 focus()+select()+execCommand('insertText')
   ——同一 eval 完成，跨 eval 分步焦点丢失
6. 【关键】显式点「从数据库中搜索」（opts.dbSearch:'force'）——见下方
   「前端过滤截断」陷阱，关键词范式必须走数据库搜索
7. 结果锚点:标题=数据库搜索"kw"的结果 + 列表项全部含关键词
   （高亮拆分形态下 leaf 是关键词片段，天然满足）
   或「暂无搜索内容」终态（且 inputVal 确为关键词——输入没生效不算无结果）
8. 加选:点「添加左侧全部字段值」;无此按钮 → 手动全选(行级去重，见陷阱)
9. 勾选证据锚点:「已添加(N)」计数真实增加(不增=早点击丢失，重试一次)
10. 确定 → 弹层关闭锚点
```

僵死弹层（popup-dead）重开重试：输入 onChange 不触发 + db-search 点击不发请求
（网络零流量）→ 取消关闭 + 重开 + 就绪锚点 → 内核重跑一轮；再失败如实报错。

## 输入通道:为什么必须 execCommand 且同一 eval 内

order-detail 双通道对照实证(2026-08-27):

| 通道 | 表现 |
|---|---|
| CDP `page.insertText` | DOM `input.value` 变了(锚点读到了),但 **React onChange 不一定触发**——点 db-search 按钮后组件拿**空 state** 查询,列表空 15s 超时。时灵时不灵(同页同字段两种结局) |
| eval 内 `execCommand('insertText')` | 完整 input 事件序列触发 onChange → 组件自动数据库全量搜索,数秒渲染完整结果(「成都万科」58 项) |

关键细节:**focus + select + execCommand 必须在同一次 eval 内完成**。跨 eval 分步时
聚焦丢失,execCommand 返回 false(quote-detail 时代「iframe 内不可靠」的结论真正原因)。

## 陷阱清单

1. **前端过滤截断（最严重，静默漏加）**：弹层带「默认展示前1000条选项值，
   超出此范围请直接搜索」时，打字触发的自动搜索走哪条路**不确定**——默认
   1000 条已加载时是**前端过滤**（仅 1000 条内匹配），未加载时才触发
   queryForMultiEnum 数据库搜索（全量）。实证（2026-08-27）：同关键词「成都万科」
   前端过滤加 6 项、数据库搜索加 58 项，查询结果 14 vs 6022 条——**静默丢 98%**，
   而断言「至少一项含关键词」完全发现不了。对策：输入后**显式点「从数据库中
   搜索」按钮**（dbSearch:'force'），锚点要求标题=数据库搜索"kw"的结果。
   「超出此范围请直接搜索」是页面的官方指引，照做。点「添加左侧全部字段值」
   **之前**可拍 AX 快照互证：快照里弹层整貌（截断警告+列表项数+已添加计数）
   直接可见，列表项数≠预期全集即拦截（见 anchor-assert.md §4.2）。
2. **高亮拆分 span**：搜索结果项内关键词被拆成独立 span（`成都万科` + `物业服务有限公司`）
   ——manual-all 兜底逐 leaf 点击会**一项多点（选+取消）**，必须向上聚到行级容器、Set 去重
3. **清空 no-op**：「调 fill 函数传空列表」≠清空——fillEnumMultiSelect 空列表直接 return，
   清空从未执行。清空必须独立实现（开弹层→清空按钮→确定）且锚点验证字段确实为空
4. **断言语义随筛选语义变**：关键词模式下断言 = **正向条件值至少一项含关键词**；
   条件解析必须拆 posValues / negValues（notIn 出厂排除默认不算命中），否则关键词
   「关联」会被排除条件「关联方」假阳性命中
5. **弹层僵死（popup-dead）**：弹层在某些状态下进入僵死——输入 onChange 不触发、
   db-search 按钮点击也不发请求（网络零流量），**reload 无效但取消关闭+重开即愈**。
   对策：db-search 兜底也超时后定性 popup-dead，重开弹层重跑一轮内核。
6. **settle 丢失回归**：合并/重构弹层逻辑时容易丢掉「打字前 settle」——弹层刚开
   立即 execCommand 会不触发 onChange（输入处理器未挂好）。settle 800ms 是
   实证过的必要等待，重构后必须回归验证。
7. **搜索竞态**：输入后列表可能停留在旧内容，锚点用 every(item 含 kw) 判完成；
   「暂无搜索内容」必须同时校验 inputVal（输入没生效 ≠ 无结果）

## 断言语义

```javascript
// parse 阶段:按 functionalOperator 拆正向/排除
if (/^not/i.test(String(c.functionalOperator))) negValues.push(...vals);
else posValues.push(...vals);

// 断言阶段:关键词只需命中正向值
for (const kw of expected.keywords) {
  const hit = posValues.some((x) => String(x).includes(kw));
  if (!hit) throw new CommandExecutionError('关键词「' + kw + '」无匹配条件值…');
}
```

两层断言依然强制:UI 面(字段显示文本含匹配项)+ 真实值面(查询 payload 正向条件)。

- [ ] **全集验证**：加选项数 = 数据库搜索结果数（标题=数据库搜索"kw"的结果），

- [ ] 跨月日期 + 关键词组合
- [ ] persistent 重复运行幂等（残留→清空→重设全链）
- [ ] 重构回归：合并/修改弹层逻辑后必须重跑全部 case（settle 丢失这类回归
      只能靠回归测试抓）
